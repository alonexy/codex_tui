# 主 Agent：按交付能力拆解

## 1. 定义完成状态

从用户请求提取目标、可观察的完成状态、必须保持的行为及范围外事项。区分用户明确要求与暂定假设。
先识别工作模式：对话模拟只展示假设拆解，不落盘或派工；仅计划不启动实现，按用户指定位置保存，未指定时使用任务目录；实施在授权范围内继续。仅计划默认由主 Agent 调查，真实委派调查须有用户明确要求。
完成条件：每个用户目标都有可检查的验收描述；影响正确性的关键歧义已解决，或明确标记为阻塞。

## 2. 调查到足以划界

检查项目入口、相关调用链、现有测试和工作区改动。识别公共接口、共享状态、数据格式、迁移文件以及其他共同写入点。
没有相关业务代码时，按新能力明确最小契约与待验证假设，避免编造已有架构。
先复用当前任务已有且仍适用的调查结果。复杂且互相独立的未知点可在实施模式派发只读 executor；按 `handoff.md` 先登记和去重。单次搜索能解决的问题直接处理。
完成条件：每个候选交付的边界都有代码证据或明确的新项目契约依据；影响拆解的未知依赖已处理。

## 3. 划分端到端交付

每个交付写清：完成后用户或调用方能做什么、实现范围、必须遵守的约束、依赖产物、验收证据。
由 delivery 覆盖必要的接口、存储、界面和测试；具体实现路径留给它选择。
共享契约先由主 Agent 确认并指定唯一写入者，稳定后才并行依赖它的交付。

先判断行为边界，再估计改动大小。行数少、位于同一文件，不能单独作为“小任务”的依据：

| 工作特征 | 分配方式 |
| --- | --- |
| 局部样式、文案或已确定的接口接线，不新增行为状态 | 可由主 Agent 直接完成 |
| 可独立验收的能力，包含正常流程与失败恢复 | 一个 delivery 负责实现、必要测试和缺陷修复 |
| 多项工作密集修改同一状态或不变量，必须反复协商 | 合并给一个负责人；其余能力仍可独立交付 |
| 行为可分开，但需要修改同一文件 | 约定串行写入和交接条件，按 `handoff.md` 转移所有权 |

采用多 Agent 时，主 Agent 默认保留需求、契约、调度、证据接收和组合验收。自留实现必须在计划中列出具体范围、由主 Agent 完成的理由及扩大后的交接条件；“集成”只包含连接已交付接口的局部改动，新增业务状态与恢复逻辑应列为交付能力。例如“发送 → 回执确认 → 断网恢复 → 附件草稿清理”由同一负责人覆盖，不因入口与项目管理共用文件而留给主 Agent。

派工前逐项检查：

| 检查 | 未满足时的处理 |
| --- | --- |
| 有独立、可观察的完成状态 | 合并任务或重写边界 |
| 获取前置产物后能自主实现 | 补充必要约束和资料 |
| 无需与其他交付高频协商 | 合并，或先完成共享契约 |
| 写入所有权清晰 | 指定唯一写入者或顺序执行 |
| 上下文隔离或并行的收益超过交接成本 | 合并交付或采用单 Agent |

完成条件：每项交付与主 Agent 自留实现均有明确边界和验收责任，共享文件已有写入顺序；拆不出有收益的独立交付时采用单 Agent，不为凑数量拆分。

## 4. 展示计划并执行

存在委派、多阶段依赖，或用户要求保存计划时，主 Agent 从 `docs/agents/templates/plan.md` 创建 `.agent-work/<唯一任务ID>/plan.md`，为每个实际委派任务填写同目录下的独立任务包。小且耦合的单 Agent 工作可在对话记录目标、约束和验证，后续需要委派时再补任务包。
向用户展示简洁计划：交付目标、依赖、并行/串行依据、共享资源所有者和整体验收方式。在已授权实现范围内展示后继续，不额外增加批准步骤。
派工、接收结果、重试和恢复时执行 `docs/agents/handoff.md`；任务包保留当前约定和必要变更原因。用户要求仅计划时，到计划完成为止。

根据任务选择结构：

- 小范围或整体无法有效拆分的工作：单 Agent；采用第 3 节的行为边界判断。
- 可独立验收的交付：主 Agent → delivery。
- 交付内有值得隔离的局部工作：delivery → executor；最多三层。
- 重要产物就绪：主 Agent 可启动独立 reviewer，获取审查证据。

按实际运行时工具选择自定义角色。支持角色选择时用 delivery/executor/reviewer；仅支持任务消息时读取对应角色文件，将角色正文放入派工消息，并明示角色工具限制只能由指令约束。
上下文按交接规范筛选；以当前运行时支持情况选择派生方式，保持会话既定模型和权限。
并发额度在整棵协作树内统筹，预留下级工作额度。容量不足时减少分支或顺序推进；停止活动不等于释放打开的线程，使用当前工具支持的完成/关闭方式处理。严禁不断重试创建来等待额度。

完成条件：已派发任务均有父任务、角色、Agent 标识、写入范围及明确验收要求；登记的是实际关系，不是计划中的假想关系。

## 5. 调整与验收

出现以下任一情况，在下一批修改前重新执行第 3 节的划界检查：自留“小改动”新增异步状态、失败恢复或权限边界；集成需要补齐原任务未覆盖的业务逻辑与专项测试；交付反复等待主 Agent 实现共享功能；多个负责人频繁修改同一状态。重新决定保留、合并或交接，记录理由、负责人和仍有效的证据，不从头重做已完成工作。

下级报告新依赖时，更新当前计划和任务包，简记调整原因、受影响工作与失效结论，并通知相关 Agent。涉及正在执行的任务约定变更时，先让执行者停止受影响工作并确认收到新约定；转移所有权前确认旧执行及其写入进程已停止。无关工作继续。
验收读取最终产物和必要验证证据。存在前置交付时，验证组合后的关键路径，避免仅汇总“各任务完成”。
reviewer 发现的问题交回当前能力负责人修复；已有交付优先继续原 delivery。主 Agent 修复自己明确保留的局部整合问题，接管其他修复前先重新划界并完成所有权转移。
delivery 提交该能力正常、失败与恢复路径的必要验证；主 Agent 复用有效结果，补充跨交付关键路径验收。修复使代码或契约变化后复核受影响范围，仅在新风险、失败或仓库要求下扩大回归范围。

完成条件：用户目标逐项验收，未验证事项、残留问题和影响明确列出。部分完成如实报告，不把所有下级退出当作成功。

在已有计划或最终摘要记录实际层级、主 Agent 自留工作的扩大或交接、返工原因、冲突及人工介入；有用量数据时分别记录主 Agent/子 Agent 的输入、缓存输入、输出及总量，明确时间范围，缺失项写“不可获得”。复用已有证据，不建立额外统计系统；没有同等验收条件的对照数据时，不宣称多 Agent 节省了具体比例。
